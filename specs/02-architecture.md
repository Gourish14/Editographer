# 02 — Architecture (local, no-install)

Everything runs on one Windows laptop as three processes plus Ollama. No Docker, no external database, no message broker, no object storage server.

```
Browser (Angular UI)
      │  REST + SSE  (http://localhost:8080)
      ▼
Spring Boot backend  ──── H2 file database (data/editographer.mv.db)
      │  HTTP (localhost:8090, shared token)          ▲
      ▼                                                │ progress callbacks
Python AI worker (FastAPI)  ───────────────────────────┘
      │  HTTP (localhost:11434)
      ▼
Ollama (Qwen3 4B director, Qwen2.5-VL 3B captions)

All processes read/write the same local folder: media/
```

## Processes and ports

| Process | Tech | Port | Role |
| --- | --- | --- | --- |
| Backend | Spring Boot 4, Java 25 | 8080 | REST API, uploads, job queue, progress (SSE), serves the built Angular app |
| Frontend | Angular | served by backend (dev: 4200) | Upload, settings, prompt, live progress, player |
| Worker | Python 3.12 (uv venv), FastAPI + Uvicorn | 8090 (localhost only) | All analysis, planning (brain), rendering |
| Ollama | Ollama for Windows | 11434 | Runs the local LLMs |

In normal use the user opens only `http://localhost:8080`. Angular is built once by `setup.bat` and copied into the backend's static resources.

## Communication

- **Browser → Backend:** REST JSON; uploads via tus (resumable, needed for 16 GB .OSV files); progress via Server-Sent Events.
- **Backend → Worker:** `POST /jobs/analyze` and `POST /jobs/render` with the job id and settings. The worker returns `202 Accepted` immediately.
- **Worker → Backend:** `POST /internal/progress` and `POST /internal/complete` with `X-Worker-Token` (random token generated by `setup.bat`, stored in `config/local.env`).
- **Worker → Ollama:** HTTP `/api/chat` with `format: json` and `keep_alive: 0` (unload after each call to free VRAM).

## Job queue (replaces RabbitMQ)

- Jobs are rows in the H2 `job` table (`QUEUED → RUNNING → DONE / FAILED`).
- A Spring `@Scheduled` dispatcher runs every 2 s: if the worker reports idle (`GET /health` → `busy: false`), it sends the oldest queued job.
- The worker processes **one job at a time** (GPU lock). Analysis jobs have priority over render jobs.
- On backend restart, `RUNNING` jobs are reset to `QUEUED`; the worker's analysis cache makes re-runs cheap.

## Storage (replaces MinIO)

All paths are relative to the project root and configured once in `config/local.env`.

```
media/
  uploads/{projectId}/{assetId}.{ext}     original files, never modified
  proxies/{assetId}.mp4                   720p proxy (or Osmo .LRF copy)
  cache/{fileHash}/analysis.json          analysis results, keyed by content hash
  cache/{fileHash}/frames/ depth/ masks/  intermediate data
  renders/{renderId}/preview.mp4
  renders/{renderId}/final.mp4
  renders/{renderId}/plan.json            the edit plan used
```

Downloads are streamed by the backend from `media/renders/`.

## Scaling later (not built now)

If the app later moves to a server: H2 → PostgreSQL (Spring datasource change), `media/` → MinIO (storage interface already abstracted as `StorageService`), dispatcher → RabbitMQ. Keep these behind interfaces so the swap is config, not a rewrite.
